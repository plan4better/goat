# GOAT GeoAPI

OGC API - Features and Tiles for GOAT layers, served from DuckLake with DuckDB.

## Overview

GeoAPI serves the **data** of a layer; core holds its metadata. It provides:

- **Features**: OGC API - Features with CQL2 filtering, sorting and paging (`/collections/{layerId}/items`).
- **Vector tiles**: OGC API - Tiles as MVT, from prebuilt PMTiles where they exist (filtered ones too, when manby built them), generated on the fly by DuckDB otherwise.
- **H3 hexagon tiles**: a point layer's tile route with `?h3=` draws H3 cells (count, or sum or mean of a field) instead of the points, for the style render `h3`. Computed per request with DuckDB's h3 extension, which geoapi's pool loads; the zoom picks the resolution under `auto` (`goatlib.style.h3`). A point counts in the hexagon that contains it, at every resolution (rolled up from fine cells, a few percent of the points landed in a coarse hexagon beside them). A tile reads its points 2.5 average cell edges beyond its border, more than the widest hexagons reach (about 2.2 edges; two edges missed points of some border cells outside central Europe), so neighbouring tiles agree on the cells they share. Each tile scans the table through its `bbox` column: on a layer written in spatial order (goatlib README, "Rows are stored in spatial order") that reads only the row groups near the tile, on one written before it the whole table. `ids` counts only those features (an atlas page's feature); the browser cannot filter cells the way it filters a layer's features. The classes are not computed here: processes writes them into the style (per resolution) when it is saved.
- **Raster files**: value tiles (the cells' values, which the browser colors and shades) and their description (`/collections/{layerId}/coverage/tiles/WebMercatorQuad`), colored WebP tiles for image renders and their description (`/collections/{layerId}/raster/tiles`), the file's bounds, band statistics, class breaks and point values of a raster layer's COG (`/collections/{layerId}/raster/...`).
- **Editing**: create, update and delete features and columns, and batch edits of a bundle's network layers.
- **Expressions**: validating and previewing computed-column expressions.
- **Download**: exporting a layer of a published project in common GIS formats.
- **Explorer snapshots**: a public transport bundle as the compact, indexed Parquet files the Explorer loads into DuckDB-WASM (`/bundles/{bundleId}/explorer`).

The collection id is the layer UUID. The full, current route list is the OpenAPI document at `/api/docs`.

## Why a Separate Service?

Tiles and features are the latency-critical path every map view hits. Keeping them here, and long analytics in processes, means a heavy job never slows down map rendering.

## Storage Model

- Each layer is one DuckLake table, `t_<layer id without hyphens>`. New layers live in schema `main`; layers created before the flat layout stay in their old `user_<id>` schema and are found by an indexed lookup in DuckLake's own Postgres catalog.
- **Feature ids are `rowid + 1`**, because MapLibre treats an MVT feature id of 0 as "unset". The bundle editor keys on the layer's `id` column instead, since deletes within one batch would shift rowids.
- **Promoted catalog datasets** are not DuckLake tables: they are parquet files under `CATALOG_LAYERS_DIR`, exposed through an in-memory view that adds the same `rowid`. They are read-only.
- **PMTiles** live in `TILES_DATA_DIR` (user layers) and `CATALOG_TILES_DIR` (catalog layers). They are built outside geoapi, by goatlib: every import builds them for the layers it creates, a bundle's map members included (cut on the fly, a region's worth of a network's shape lines runs to several MB a tile), and goatlib tasks rebuild them after edits. goatlib builds them with manby and records a marker in the archive's description (`MANBY_MARKER` in `packages/python/goatlib/src/goatlib/io/pmtiles.py`); tiles without it (built before manby) are never filtered by geoapi: older point tiles merged nearby points at every zoom, and some had no feature ids. A tile deeper than the stored pyramid is cut from its nearest stored parent with `manby overzoom` at detail 16, which keeps the stored tile's precision.
- **Workflow previews** are parquet and PMTiles files under `/app/data/temporary/user_<id>/…`, read with `?temp=true`. The same builder makes their tiles as every layer's, so preview features have ids too, and a polygon result has its label points in an `_anchor.pmtiles` beside the tiles.
- **Raster layers are COG addresses** (`layer.url`, `data_type = 'cog'`), read in place over HTTP with goatlib.raster (rio-tiler); nothing is copied. A raster promoted from the catalog is the exception: the catalog bucket is private, so the `catalog_materialize` job copies its GeoTIFF beside the parquet copies (`CATALOG_LAYERS_DIR/t_<id>.tif`) and geoapi and processes read that file, found by the layer's id; it has no `url`.
- **The browser colors raster values; geoapi only reads them.** A color range (in classes too), categories with classes and a hillshade draw value tiles: each pixel holds a cell's value as a code (`goatlib.raster.values`), and MapLibre colors them (`color-relief`) and shades them (`hillshade`) from one source, so a color edit sends no request and there is no separate elevation route. A value tile's address names everything its pixels depend on (the band or formula, the resampling, the encoding's base and step, the values version), so it reads no statistics, and every pod, and later a CDN, answers it with the same bytes; the description names the encoding and its link template carries it. The values version is the row's version (its address and its update time to the microsecond) plus, for a remote file, its ETag or Last-Modified from the HEAD of the ten-minute address check, so a file replaced at the same address gets new tile addresses. Value tiles are therefore cached forever by URL (`immutable`) when their version follows the file, a stored file or a remote one whose host gives a validator: the URL changes with the file, the encoding and the packing version (`ENCODING_VERSION`). Colored tiles are cached by the same rules (one helper answers both routes): their `v` is the same values version, given by their own description, and their URL carries the coloring. Their pixels also depend on what the URL does not name: goatlib's `colorize`, and for a coloring without a domain (or a one-band image) the range from the file's statistics (`_band_range`); a change in either bumps `ENCODING_VERSION`, and goatlib pins reference colored tiles as it pins value tiles. Both descriptions are asked again soon (`max-age=60`): `private` when read with a sign-in, `public` without, as the tiles. A remote file without a validator (no ETag or Last-Modified, or a HEAD the host refuses) keeps its version when it is replaced, so its tiles are kept an hour, and a tile whose `v` is not the layer's current values version (an old description, none, or a pod whose row is older) is answered with `no-store`. A tile read with a sign-in is `private`, which no shared cache keeps, and one read without is `public`; the web sends no token with its tile requests, so while read authorization is not enforced (`ENFORCE_READ_AUTHZ`, off by default) every map tile is `public`, a private layer's included. Before a shared cache such as a CDN sits in front of raster tiles, enforce read authorization, which needs the web to send its token on tile requests. Image renders, colors over float values of an unknown range (the codes then cover only a stand-in span and cannot place them), and colorings with more than 4096 stops whose coloring fits in a URL (longer ones are reported as not supported) use colored tiles whose URL carries the coloring (`?style=<token>`: base64url JSON of the coloring the web derives from the style, `goatlib.raster.token`); their colors follow the browser's semantics of the coloring before the service existed.
- **The web asks for 512 px raster tiles, and only where the file is.** The value tiles, their description and the colored tiles take `tilesize`: 256 (the default, for other clients) or 512. A 512 px tile is the same tile z/x/y, the same area at twice the resolution, so a map needs a quarter of the requests for the same view. The size is in the URL, so caches keep the two apart, and a 512 px address carries an `ENCODING_VERSION` that a geoapi without `tilesize` does not have: such a geoapi reads a 256 px tile for it, but finds another values version in its `v` and answers `no-store`, so no cache keeps it there. The description is for the size asked for: its `maxzoom` (where the tiles show the file's cells at their own size; rio-tiler estimates it for 256 px) is one less for 512 px, never below the file's minzoom, and its link carries the size. It also names the file's `bounds` in degrees, as TileJSON does, and the web puts them on its sources, so MapLibre asks only for the tiles that touch the file instead of the tiles around it, which would answer 204. The value tiles' description also names the file's bands (`names`, as the info gives them), so a map's popup labels its values without asking for the info; its ETag names the description's shape (`VALUES_DESCRIPTION_SHAPE`), so a description that gains a field is sent anew instead of revalidating the one a browser kept, while the tiles keep their URLs. An image render reads the colored tiles' description (`/raster/tiles`): the same `maxzoom` and `bounds` from the file's header alone (no band, no encoding, no statistics), the values version (`goat:version`) its tile link names, and the bands' facts from the header (`goat:bands`: count, data type, scaling, color table, names, the bands that hold values, each band's color interpretation), from which a map tells whether the pixels are the file's 8 bit values and which bands they are (an image draws the bands its file marks red, green and blue, goatlib `image_bands`; a popup reads them there, spec 9.7); its ETag names that shape (`IMAGE_DESCRIPTION_SHAPE`). A file with a color table also gets the table's every entry with the band it colors (`palette`, from the header too, at most an 8 bit band's 256 entries): the web draws such an image from that band's value tiles in these colors, so its map holds every cell's code, also where entries share a color (the colored tiles stay for other clients). It is the whole table, not the codes the statistics found in an overview, so a rare code the overview missed still gets its color. The info (`/raster/info`) gives the same `color_interp` and `palette`. Past `maxzoom` MapLibre magnifies the deepest tiles with the layer's resampling, as for value tiles, instead of asking for new tiles that only magnify the file's cells. The image draws once its description has answered, as value renders wait for theirs; when there is none, it draws with the layer's stored extent (which core stores from the same header) and without a `maxzoom`.
- **Tiles are lossless WebP at libwebp's effort 50.** Encoding is most of a tile's server time and holds the GIL, so tiles are read one after another per process. For a lossless image GDAL's `QUALITY` is libwebp's effort, not a loss: 50 gives the same pixels at about the size of the default 75 in less time. The bytes differ from 75's, the pixels do not, so cached tiles stay valid (no `ENCODING_VERSION` bump). An 8 bit RGB image is colored from its bytes without a float copy, and a file is read without rasterio's AWS session unless GDAL reads it through S3 (an `s3://` path; an http(s) address, a public bucket's included, is read unsigned). goatlib opens an https address by its `/vsicurl/` name, because rasterio's own open takes one naming amazonaws.com for S3: geoapi runs without AWS credentials in its environment, and botocore would then look for them up to the cloud's metadata service, about two seconds for every tile of such a file (goatlib's `gdal_env` and `_gdal_path`).
- **A COG layer's extent is core's to store; geoapi's routes only read.** The `bounds` route reads the file's header and answers its bounds in EPSG:4326. core calls it when it creates the layer or gives it another address and stores them as `customer.layer.extent`, so the route reads the layer row afresh rather than the copy kept for a minute; the web calls it for a layer stored without one. No raster route writes the layer row: tiles are the hot path, public maps read anonymously, and the routes must work with a read-only role. Layers created before core stored extents are filled once by an operator: `python -m geoapi.scripts.backfill_raster_extents [--dry-run]` in geoapi's image (it has the raster reader core lacks) reads the same bounds and writes only rows without an extent, leaving `updated_at` alone.
- **Explorer snapshots** live in `DATA_DIR/explorer/<bundle id>/r<revision>.s<schema>/`, one per bundle revision, built by geoapi on the first request for it (`packages/python/goatlib/src/goatlib/bundles/explorer/snapshot.py` does the conversion). The manifest answers 202 while the build runs, and a failed build for five minutes after (so a broken feed is not rebuilt on every poll) unless the request says `?retry=true`, which the Explorer's Try again does; the files' URLs name the revision, so they never change, and browsers keep them for a month (`FILE_MAX_AGE_SECONDS` in `routers/explorer.py`). A build reads the revision and the DuckLake snapshot id together under the bundle's advisory lock, taken shared (`goatlib.bundles.locks`) — a writer of a bundle's layers takes it exclusively from its revision claim to its DuckLake commit — and reads every table at that snapshot. One build at a time per pod, on its own DuckLake connection, at most 512 MB plus spill; a `.building-r<n>` marker keeps a second pod from building the same revision. Shapes go in simplified to 2 m (`SHAPE_TOLERANCE_M`), a thousand at a time so the build stays within its memory, with every stop placed along its trip's shape: playback moves vehicles along the lines the map draws. A trip without a shape gets the line through its stops as its shape, the same line the bundle's `shape_lines` member draws (`packages/python/goatlib/src/goatlib/bundles/importers/pt_network/stop_chains.py`), so shapeless feeds draw, play and click like any other. The previous revision, or a snapshot of an older schema, is kept an hour for downloads in flight; stale temporary folders and snapshots untouched for 30 days are removed hourly.

## How It Stays Consistent

- **Reads are pinned to a DuckLake snapshot.** A background thread polls for new snapshots and swaps in a fresh, warmed connection off the request path. After a write, the pod also publishes on the Redis channel `ducklake:changed` so other pods refresh at once; the poll is the fallback when Redis is unavailable.
- **Every write deletes the layer's PMTiles**, so tiles fall back to dynamic generation until the scheduled Windmill task `rebuild_edited_pmtiles` rebuilds them once the layer has been idle for a while. Schema changes do not create a DuckLake snapshot, which is why the files are removed rather than trusted.
- **Generated columns are filled by the writer, never by the client.** A `serial` (running number) or `uuid` column, declared by `kind` in the layer's `field_config`, gets its value on every create path — single and batch creates, and the bundle editor's new and split edges — and a client's value for one is ignored. An update that would change one is refused (400); sending the stored value back, as editors do, is fine. A serial number is never handed out twice: it is `max(high-water mark, max(existing), start - 1) + 1`, where the high-water mark is the highest number the column ever handed out, kept in core's `customer.layer_serial_counter` — so deleting the feature with the highest number does not free it. Adding such a column to a layer with rows backfills them once, in `rowid` order, and sets the mark; dropping the column forgets the mark and renaming moves it, so a column re-added under the same name starts over. A layer without a mark (an import, or before core's migration ran) continues from its own highest number. The rules live in goatlib (`goatlib.utils.generated_fields`; defaults, allowed values and computed columns in `goatlib.utils.field_config`), so a workflow adding rows to an existing dataset fills them the same way.
- **An existing number column can become a serial** (`PATCH …/columns/{name}` with `kind: "serial"`), keeping its name and values: hand-typed project numbers that workflows already reference. It is refused, with the offending values named, for duplicates or fractions; blank rows get numbers after the highest; the mark starts at the highest value, so gaps are never filled. A non-BIGINT column is rebuilt as BIGINT under the same name (moving to the end of the column order) rather than `ALTER … SET DATA TYPE`d: after an in-place INTEGER→BIGINT promotion, `max()` fails on a connection that had read the column's statistics. `kind: "number"` turns a serial back and drops its mark. Columns of a bundle member cannot be converted, and nothing converts to `uuid`.
- **Serial numbers are assigned under a per-layer Postgres advisory lock** (`services/layer_write_lock.py`; its key is defined once in `goatlib.utils.layer_lock`, so goatlib's `finalize_layer` takes the same lock when a workflow's "Save as dataset" adds rows to an existing dataset). The write manager's `threading.Lock` serializes writes within a pod only, and DuckLake commits two concurrent appends to one table without a conflict, so two pods reading the same `max` would hand out the same number. The lock is transaction-scoped (`pg_advisory_xact_lock`), so a pod that dies releases it. Every feature create, update and replace takes it and reads `field_config` under it (one extra round trip), because any number column can become a serial at any moment and a write that read the old definition must not slip a typed-in duplicate past the conversion; the bundle editor and the add-column backfill take it only for serial columns. The high-water mark is read and advanced in that same transaction, after the DuckLake rows are in: a failed write leaves it alone, and if storing it fails after DuckLake committed, the rows still carry the numbers, so `max` covers them. UUIDs need no lock.
- **Bundle edits are optimistic.** The client sends the bundle revision it edited; a stale revision answers 409. The edges and nodes layers are written in one DuckLake transaction, then a `bundle_artifact_rebuild` job is sent to processes (`GOAT_PROCESSES_URL`).
- **Caches**: layer metadata and PMTiles-served tiles are cached in Redis, a filtered tile under the file's version and the filter's digest, so a rebuilt file never serves the tiles of the one it replaced. Raster tiles are not kept in Redis at all: a color edit no longer asks for tiles, and their versioned addresses let each viewer's browser keep them (a tile whose address names the current values version for good, or an hour when a remote file's host gives no validator, then an ETag check); a CDN in front of geoapi can later serve many viewers. A raster file's statistics are kept per pod for an hour under the values version, so a replaced remote file is read again. Every band's class breaks for each class method and count (`goatlib.raster.stats.precomputed_breaks`) are kept the same way: `/raster/info` gives them with the statistics, so the style panel switches methods without a request. They equal the classes a style check writes: every method but equal intervals (quantiles, natural breaks, standard deviation, heads and tails) classifies the whole band whatever the style's `render.domain` (only equal intervals split the domain). A count's list can be empty. A whole-number band with few codes also lists how many cells of the overview hold each (`counts`, in the order of `values`), so the class editor shows each category's share. An alpha band (an orthophoto's transparency) gets neither statistics nor breaks, as goatlib's reader takes it, and the tile routes answer 400 for a band or formula naming it, in validation's words; `count` is still the file's band count. Tiles never wait for them: they are kept apart from the statistics, which a cold layer's first tiles read; the infos of a cold layer wait for one computation without a read slot; that computation holds one of the layer's read slots only to read every band's values (one overview read), and classifies them on threads of its own after releasing it. A failed computation never fails the info: a band without breaks answers `{}`, the statistics are served, the failure is logged without the file's key and is remembered for 30 seconds for the breaks only, so the file's tiles are not marked failing and the next info does not compute them again at once. Dynamic tiles and feature responses use ETags derived from the layer version and the pinned snapshot instead; a filtered tile cut from PMTiles gets one from the file's version, the filter and z/x/y, with `Cache-Control: no-cache`, so a browser revalidates and an unchanged tile answers 304 without any work. Without Redis everything still works, only slower.
- **Credit metering (billing on only)**: tiles and features are counted per organization, layer and service in memory, and a background task writes the counts to Redis every few seconds (`middleware/credit_metering.py`), so no response waits for Redis; goatlib's `traffic_rollup` charges them. Metering uses the tile cache's Redis but not its switch: with `TILE_CACHE_ENABLED` off it still counts. Downloads are charged by the download route itself, after the response: the export's run time as compute and the zip's size as egress, directly in core's database, like a layer export job.
- **A filter is checked before any query**: every client filter (the `filter` parameter of the features and tiles routes) passes `cql_filter_query` in `dependencies.py`, which answers 400 when the filter is over a request ceiling (`over_request_limits` in `packages/python/goatlib/src/goatlib/filter/validate.py`) or does not parse. The ceilings only protect the parser and DuckDB and lie well above the save limits core applies, so a filter saved over a save limit still filters. The parse is the query builder's own (cql2-json after `goatlib.filter.normalize`, so the older spellings still pass), because the builder skips a filter it cannot parse and would answer with every feature. A cql2-text filter has to be parsed to be measured and is held against the ceilings as the CQL2 JSON it stands for. The verdict is remembered per filter text, since a screen of tiles brings the same filter once per tile. A filter that parses but names a field the layer lacks is not caught here: the builder still skips it, so the map shows every feature (tools, exports and the statistics of processes refuse such a filter instead, `checked_cql_filter`).
- **`properties` on the items route picks what each feature carries**: an empty value returns the features without properties (a layer's and a workflow result's alike), and names the collection lacks are left out instead of refused. The browser's clusters (style spec 8.2) ask for only the fields their style reads, so a style naming a field its dataset no longer has still shows its points. The single-feature and tile routes answer 400 for an unknown name.
- **Points of lines and polygons for the style**: `label=true` adds one label point per polygon (layer `default_anchor`, from the `_anchor.pmtiles` beside the tiles, or `ST_PointOnSurface` in DuckDB), and `decoration` adds start, end or center points of each line (layer `default_decoration`), several kinds in one request (`decoration=end,center`) with each point's kind in `_decoration`. Both carry their feature's properties, as many as the main layer: the style draws labels, arrows and markers on them by class or by attribute (style spec 15), and the map's popup and click to filter on a marker or a label at a point of a line read the line's attributes from the point itself. Decoration points are computed from the whole line, so a line cut by tile borders still gets one of each; for that they always come from DuckDB, from the lines of the main layer: the same filters, row group pruning on the `bbox` column and feature limit (neither limit has an order, so a tile at the limit can draw a point on a line it does not draw). A multipart line counts as one line, its parts joined where they meet end to end (which can turn a part around to follow the others), else its longest part.
- **"In the last N days" is resolved at the entry**: the panel saves it as `daysAgo(n)`, which counts back from the day the filter is read (`goatlib.filter.normalize`). Every cache here keys on the filter text `cql_filter_query` passes on (the Redis tiles and prepared filters by `request_digest`, the ETags), so a filter with `daysAgo` is passed on normalized, with the date it means today: the same filter all day, another one tomorrow. A day, not the moment, for that reason; the fast filtered tiles translate the date as any other.

## Filtered Tiles

A tile request with a filter (dashboard widgets, cross filters, the layer filter in the map) used to be rendered by a DuckDB query over the layer for every tile: slow on a big layer at low zoom, capped in features per tile, and under a burst of requests enough to take a replica's CPUs and most of its memory. When the layer's PMTiles carry the manby marker, geoapi filters the stored tile instead (or the parent it is cut from) with `manby overzoom --feature-filter-file`, which is quick enough to do per request. `TileService.get_filtered_tile_from_pmtiles` is the entry point.

- **DuckDB still answers everything else**: a layer without PMTiles (just uploaded, or edited), PMTiles without the marker, `dynamic=true`, `decoration`, `properties` or `limit`, H3 hexagons (`h3`, which count the features instead of drawing them), a filter manby cannot express, and any manby failure or timeout (logged). Whatever the stored-tile path cannot answer the way DuckDB would goes to DuckDB, so a filter that worked before still does, only slower.
- **`services/tile_filter.py` translates the CQL2 filter** and returns nothing rather than a filter that could differ from DuckDB's. Its module docstring holds the rules (NULL handling, column types, areas); `tests/test_filtered_pmtiles_equivalence.py` compares both paths on real tiles. A filter DuckDB's query builder drops whole (one naming a field the layer lacks, saved before the column was dropped) is no filter on the stored tiles either, as it is none in DuckDB's tiles. A field the layer has but its tiles lack stays with DuckDB: a tileset lists only the fields some feature has a value for, but a missing field is not proof that the column is empty.
- **Accepted differences**: a filtered tile holds only the features the stored tile kept, so a rare match can be missing at low zoom (as when filtering in the browser); with an area filter, a long line or a big polygon shows only in the tiles where its piece intersects the area, and with an area the features must lie outside of (`not s_intersects`) in the tiles where its piece misses it.
- **The number of manby processes per replica is bounded** by the container's CPU quota (`_manby_concurrency` in `services/tile_service.py`), so a screen of tiles cannot starve the event loop and the DuckDB queries. Without a CPU limit, and the Helm chart and compose set none for geoapi, the bound is the CPUs the process may run on: the node's.
- **The filtered tiles DuckDB draws at once are bounded too** (`_filtered_tile_concurrency` in `services/tile_service.py`): one less than the dynamic-tile threads and than the pool's connections (`GEOAPI_DUCKLAKE_POOL_SIZE`). Such a tile can take seconds (a filter manby cannot express, on a big layer) and a screen asks for many, so unbounded they held every thread and connection, and the tiles DuckDB draws without a filter (a layer without PMTiles, `dynamic=true`, H3) waited seconds behind them. The rest wait in the event loop, and a slot goes back when its thread is done, not when its request is, because a request that timed out leaves its query running. The price is that a burst of such tiles finishes a little later.

## Access Rules

- A layer of a published project is readable by anyone. Otherwise `customer.can('layer', …, 'read')` in core's database decides. **Read authorization runs in shadow mode by default** (`GEOAPI_ENFORCE_READ_AUTHZ=false`, also read as `ENFORCE_READ_AUTHZ`, the name the Helm chart sets): a denial is only logged as `read_authz.would_deny`, and the layer is served anyway.
- Writes need a user and pass `customer.layer_write_allowed`. Features of a bundle member layer are edited through the bundle routes, though columns may still be added to it; catalog layers cannot be edited.
- Download needs no token but only works for layers of a published project.
- A raster route opens only the layer row's own address, never one from the request (or for a catalog raster the copy named by its id), and only http(s) hosts that resolve to public addresses (goatlib's `url_guard`); redirects answered to a HEAD request are checked hop by hop. GDAL resolves the name again when it reads and follows redirects a server sends only to its reads, so block geoapi's and processes' outgoing traffic to private ranges at the network level too (a NetworkPolicy or firewall). Hosts inside the cluster (an object store) must be listed in `RASTER_PRIVATE_HOSTS`. A file that does not answer fails within seconds and then answers `504` at once for 30 seconds, on every raster route and without waiting for a read. The answer says what failed in plain words (goatlib's `RasterUnavailableError`: the host could not be reached, answered with an HTTP status or did not answer in time, or the file could not be read as a raster) and never the file's address, since a signed link's query is an access key; the error goes to the log, which names the file without its query and credentials. Reads run on their own threads, at most four per layer at once. A tile whose caller has gone (MapLibre drops tiles that left the view) is not read and answers 204, which no cache keeps. At `TILE_DEADLINE_S` (10 seconds), a tile read that ran (nearly) the whole time answers `504` and marks the file as failing; a tile still waiting for a reader at the deadline, or one that got its reader late, answers `503` (the readers are busy) and the file is not blamed. A started read cannot be stopped, so it keeps its slot until it returns: a slow host holds at most four threads per layer.
- An Explorer snapshot is readable by whoever may read the bundle's stops layer: member layers carry the bundle's grants, and a project holding the bundle shares them, which are the two ways core lets a bundle be read.
- A token must verify, and with `AUTH_ALLOWED_CLIENTS` set it must be issued to one of those clients (goatlib's `KeycloakAuth`). A token that fails is a 401 where a user is required; where a token is optional, the request runs as anonymous.
- With `AUTH=False`, requests without a token run as the built-in development user.

## Gotchas

- **Settings use the `GEOAPI_` prefix.** A bare name works only for the settings that read it explicitly (for example `AUTH`, `AUTH_ALLOWED_CLIENTS`, `KEYCLOAK_SERVER_URL`, `POSTGRES_*`, `DUCKLAKE_DATA_DIR`, `DUCKLAKE_PIN_SNAPSHOT`, `REDIS_URL`, `GOAT_PROCESSES_URL`, `ENFORCE_READ_AUTHZ`, `RASTER_PRIVATE_HOSTS`); everything else, such as `DUCKLAKE_POOL_SIZE` or the timeouts, must be set as `GEOAPI_<NAME>`. All settings are in `src/geoapi/config.py`.
- Point `DUCKLAKE_POSTGRES_SERVER` (and `DUCKLAKE_POSTGRES_PORT` when it differs) at Postgres directly, not through a transaction pooler: DuckLake attaches keep their catalog connections for as long as they live and are not verified behind one.
- When `POSTGRES_SERVER` is a pooler in transaction mode, set `POSTGRES_TRANSACTION_POOLER`: the query pool then caches no prepared statements and sends no TCP keepalive settings, which a pooler with stock settings refuses at connect.
- DuckDB's memory budget per pod is `GEOAPI_DUCKDB_MEMORY_LIMIT × (GEOAPI_DUCKLAKE_POOL_SIZE + 2)`: pooled cursors share one DuckDB instance budgeted for the whole pool, and the read and write connections get one budget each. Keep it under the container's memory limit with room for the catalog metadata each connection keeps outside that budget; DuckDB spills only at its own budget, so above the limit the pod is killed first. Keep `GEOAPI_DUCKDB_THREADS × GEOAPI_DUCKLAKE_POOL_SIZE` at about the container's CPUs.
- Updating a row inserted in the same DuckLake transaction leaves it with a transaction-local rowid that breaks MVT feature ids; `bundle_edit_service.py` writes derived columns in the insert itself for that reason.
- A COG without overviews is not read for zooms that would decimate it more than 8x (no tile there; statistics from its center 1024 px), so a huge file is never downloaded whole for a low zoom.
- **Start subprocesses with `await asyncio.to_thread(subprocess.run, ...)`, never `asyncio.create_subprocess_exec`.** Under uvloop the child runs the at-fork hooks before `exec` (OpenTelemetry restarts its threads there), and a lock held at fork time hangs the child and with it the whole event loop. `tests/test_overzoom_spawn.py` guards it.
- **Never let a NULL geometry reach `ST_AsMVTGeom`.** In an `ST_AsMVT` over several rows, DuckDB's spatial extension then fails with an internal error, and DuckDB invalidates the whole database instance: in the pinned pool all cursors share one, so every query of the pod fails until the pool rebuilds it, which the next query does (goatlib counts "database has been invalidated" as a connection error). `ST_StartPoint`, `ST_EndPoint` and the like answer NULL for anything but a LINESTRING.
- Never enumerate all DuckLake tables (`information_schema`, `SHOW TABLES`) on a request path: it loads every table's metadata, which takes very long on a large catalog.

## Development

Load the repo's root `.env` and run on port 8100, which is what the web app expects:

```bash
set -a && . ./.env && set +a          # from the repo root
cd apps/geoapi
uv run fastapi dev src/geoapi/main.py --port 8100

uv run pytest tests/                  # mocked, needs no services
uv run pytest tests/integration -m integration   # needs Postgres with the customer schema
```

At runtime it needs Postgres (core's `customer` schema and the DuckLake catalog), the shared data volume, and optionally Redis. The Docker image runs `fastapi run` on port 8000 with the DuckDB extensions baked in; manby comes as a Python dependency (its wheel carries the `manby` program), so the image has no tile builder of its own.
